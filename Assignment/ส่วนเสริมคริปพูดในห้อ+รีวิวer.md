## จุดเน้นภาพรวมที่อาจารย์สั่งเพิ่ม (Overall Direction)

* **โจทย์เฉพาะสำหรับสาย Cyber:** อาจารย์ไม่ได้เน้นให้ต้องคิดออกแบบตารางใหม่ทั้งหมดตั้งแต่ศูนย์ เพราะในโจทย์โปรเจกต์มีโครงสร้างตารางไกด์มาให้แล้ว แต่จะตรวจเน้นหนักไปที่ **การแบ่งสิทธิ์ (Privilege), การปกป้องข้อมูลความลับ (Data Privacy / Protection) และการควบคุมความปลอดภัยในการรัน Transaction**
* **การจำกัดขอบเขตงาน (Scope Control):** อาจารย์ย้ำชัดเจนทั้งในคาบและตอนคุยกับกลุ่มว่า **"ไม่ต้องทำทั้งหมดนะ มันใหญ่มาก"** ให้ตัดเลือกเฉพาะส่วนที่เกี่ยวข้องกับหัวข้อที่กลุ่มเลือกทำ เพื่อแสดงให้เห็นว่ากลุ่มเข้าใจ ER Diagram, เข้าใจว่าต้องทำ Transaction อะไรบ้าง, ต้องมี Query อะไรบ้าง และจัดวาง Privilege อย่างไร

## ส่วนเสริมหมวดที่ 1: การออกแบบตาราง และ Transactions (เสริมข้อ 1.1 – 1.4 ใน PDF)

### 1. การแยกตาราง Transaction การขาย (เสริมข้อ 1.1 และ 1.3)
* **คำสั่งเฉพาะกลุ่ม:** เนื่องจากระบบของกลุ่มมีทั้งการขายหน้าร้านและการขายออนไลน์เชื่อมโยงกัน และข้อมูลการขายมีปริมาณเยอะมาก อาจารย์จึงสั่งให้ **แยกตารางเก็บข้อมูลธุรกรรมการขาย (Transaction Data) ออกเป็น 2 ส่วน (แยก Entity)** ไม่เอามารวมกัน:
  1. **`In-store Sale`:** ตารางสำหรับเก็บรายการขายหน้าร้าน
  2. **`Web Sale`:** ตารางสำหรับเก็บรายการขายออนไลน์ผ่านเว็บ
* **Entity หลักที่ต้องนำมาเชื่อมโยงในกลุ่มนี้:** สินค้า (`Product`), สาขาหน้าร้าน (`Store`), แผนก (`Department`), และพนักงาน (`Employee`)

---

### 2. โจทย์ Transaction พิเศษที่อาจารย์คิดให้กลุ่มทำ (เสริมข้อ 1.2 และ 1.4)
นอกเหนือจากตัวอย่างใน PDF อาจารย์ได้ให้แนวคิด **Flow ของ Transaction สำหรับปกป้องความเป็นส่วนตัว (Privacy) ของลูกค้า** เพื่อให้กลุ่มนำไปเขียนเป็น Query และโค้ด Java ดังนี้:

* **แนวคิดหลัก:** **การอัปเดตสถานะการจัดส่ง พร้อมซ่อนที่อยู่จัดส่งของลูกค้า (Shipping Address Masking)**
* **เหตุผลด้านความปลอดภัย:** ในโปรเจกต์ของกลุ่มมีข้อมูลที่ Sensitive คือ **ข้อมูลบัตรเครดิต (Credit Card)**, **ข้อมูลการชำระเงิน (Payment)** และ **ที่อยู่จัดส่งของลูกค้า (`Shipping`)** หากส่งสินค้าเสร็จแล้วแต่ยังปล่อยให้เห็นบ้านเลขที่และที่อยู่เต็ม อาจถูกแฮกหรือนำไปสะกดรอย (Track) หาที่อยู่บ้านของลูกค้าได้
* **ลำดับการทำงานใน Transaction เดียวกันที่อาจารย์แนะนำให้เขียน:**
  1. เมื่อทำ Transaction การขาย จ่ายเงิน และจัดส่งสินค้าให้ลูกค้าเสร็จเรียบร้อยแล้ว $\rightarrow$ สั่ง **`UPDATE` สถานะของการจัดส่ง (`Shipping Status`)** ว่าจัดส่งเสร็จสิ้นแล้ว
  2. ทันทีที่อัปเดตสถานะจัดส่งเสร็จ $\rightarrow$ สั่ง **`UPDATE` แก้ไข/ซ่อนข้อมูลที่อยู่จัดส่งของลูกค้าใน Transaction Sale** โดยไม่ให้เห็นบ้านเลขที่หรือที่อยู่เต็ม แต่ให้เหลือแสดงเฉพาะข้อมูลบางส่วน (**Partial**) เช่น **เหลือเฉพาะรหัสไปรษณีย์ (Zip Code) หรือเหลือเฉพาะรัฐ/จังหวัด (State) อย่างเดียว**

## ส่วนเสริมหมวดที่ 2: การแบ่ง Roles, สิทธิ์ของ App และการปกป้องข้อมูล (เสริมข้อ 2 ใน PDF)

ในไฟล์ PDF บอกเพียงกว้างๆ ให้วิเคราะห์ว่าควรสร้าง Role อะไรบ้าง แต่อาจารย์ได้ **ระบุรายชื่อ Role และขอบเขตสิทธิ์ของกลุ่ม Smart Mart** ไว้ให้ชัดเจนแล้ว โดยต้องแยกการ Grant สิทธิ์ออกเป็น **2 รูปแบบหลัก** คือ **(1) สิทธิ์สำหรับ User (คน)** และ **(2) สิทธิ์สำหรับ App ที่ต่อเข้า Database**:

### 1. รูปแบบที่ 1: การแบ่ง Role ของฝั่งบุคลากร (User Roles)
อาจารย์ท้วงในคลิปเสียงว่า *"กำหนดแค่สิทธิ์ของพนักงานอย่างเดียวไม่ได้สิ พนักงานมีตั้งหลายตำแหน่ง"* โดยสรุปตำแหน่งที่ต้องมีออกเป็น 5 บทบาท:

| ลำดับ | ชื่อบทบาท (User Role) | ขอบเขตสิทธิ์และหน้าที่ตามที่อาจารย์กำหนด |
| :---: | :--- | :--- |
| **1** | **`Supervisor`** (หัวหน้างาน / ผู้บังคับบัญชา) | มีสิทธิ์ระดับหัวหน้างานในการตรวจสอบดูแลการปฏิบัติงานและอนุมัติรายการ |
| **2** | **`Manager` / `Warehouse Manager`** | ผู้จัดการสาขา หรือผู้จัดการคลังสินค้า ดูแลบริหารจัดการข้อมูลและสต็อกคลังสินค้า |
| **3** | **`Staff`** (พนักงานทั่วไป) | พนักงานปฏิบัติการทั่วไป มีสิทธิ์ทำงานเฉพาะส่วนปฏิบัติการของตน |
| **4** | **`HR` (ฝ่ายทรัพยากรบุคคล)** | **[กฎเหล็กที่อาจารย์เน้นย้ำ]:** **HR ดูได้เฉพาะตาราง `Employee` (ข้อมูลพนักงาน) อย่างเดียวเท่านั้น** เรื่องอื่น เช่น เรื่องขาย เรื่องสต็อก ไม่ต้องให้ดูเด็ดขาด |
| **5** | **`Admin`** (ผู้ดูแลระบบ) | มีหน้าที่สำหรับ **การเพิ่ม/แก้ไขตาราง** และทำหน้าที่ **สำรองข้อมูล (Backup Data)** จัดเก็บไว้ |

---

### 2. รูปแบบที่ 2: การแยก Account สำหรับแอปพลิเคชัน (Application Logins)
อาจารย์ระบุเจาะจงว่า ในโปรเจกต์ของกลุ่มจะมี **2 แอปพลิเคชัน** ที่เชื่อมต่อเข้ามายัง Database ดังนั้น **ต้องแยก Account สำหรับแอปพลิเคชันออกเป็น 2 Accounts**:

| ลำดับ | ชื่อ Account ของแอปพลิเคชัน | ขอบเขตสิทธิ์การเข้าถึงข้อมูลใน Database |
| :---: | :--- | :--- |
| **1** | **`In-store Sale App`** (แอปขายหน้าร้าน) | ใช้สำหรับระบบขายหน้าร้านในการเชื่อมต่อเข้ามาทำรายการขายหน้าร้านโดยเฉพาะ |
| **2** | **`Web Sale App`** (แอปขายออนไลน์ผ่านเว็บ) | ใช้เมื่อ Web App เรียกเข้ามา Connect ที่ Database<br>• **สิ่งที่เห็นได้:** เห็นได้เฉพาะ **ข้อมูลสินค้า (`Product`), โปรโมชั่น (`Promotion`), และ Transaction ที่ลูกค้าสั่งซื้อผ่านเว็บ** เท่านั้น<br>• **สิ่งที่ห้ามเห็น:** ข้อมูลหลังบ้านอื่นๆ ของบริษัทต้องมองเห็นไม่ได้ |

### 3. รายละเอียดเพิ่มเติมเรื่องการสร้าง Views และ Indexes (เสริมข้อ 2.3 – 2.4 ใน PDF)
* **การสร้าง Views (มีทั้ง `Materialized View` และ `Non-Materialized View`):**
  * บนกระดานอาจารย์เขียนระบุไว้ทั้ง 2 ประเภท คือ `Materialized View` และ `Non-Materialized View`
  * **วัตถุประสงค์ที่ 1 (การปกป้องข้อมูล / Data Protection):** วิเคราะห์ว่าต้องการปกป้องข้อมูลส่วนไหนไม่ให้บาง Role หรือบาง App มองเห็นคอลัมน์สำคัญ (เช่น ข้อมูลบัตรเครดิต หรือที่อยู่บ้านเลขที่ลูกค้า) จึงสร้าง View ขึ้นมาครอบไว้
  * **วัตถุประสงค์ที่ 2 (การเพิ่มประสิทธิภาพการสืบค้น):** ใช้ `Materialized View` เพื่อช่วยให้การดึงข้อมูลเร็วขึ้น
* **การสร้าง `Non-Clustered Index`:**
  * อาจารย์เน้นว่าเวลาเขียนวิเคราะห์ในรายงาน ต้องระบุเหตุผลให้ชัดเจนว่า **สร้าง Non-Clustered Index ขึ้นมาเพื่อเพิ่มประสิทธิภาพในการสืบค้นเรื่องอะไร**

## ส่วนเสริมหมวดที่ 3: จุดเน้นในการเขียนโค้ด Java (เสริมข้อ 3 ใน PDF)

* **การนำโจทย์เฉพาะกลุ่มไปเขียนโค้ดทดสอบ:**
  * ให้นำ Transaction ของกลุ่ม (รวมถึงเคสส่งสินค้าเสร็จ $\rightarrow$ อัปเดตสถานะจัดส่ง $\rightarrow$ อัปเดตซ่อนบ้านเลขที่ลูกค้า) มาเขียนด้วยภาษา **Java** เรียกใช้ **JDBC** และ **Prepared Statement**
  * อาจารย์เน้นบนกระดานและในคำบรรยายว่า ต้องมีกลไกควบคุม Transaction (`Transaction Control`) ตามปกติให้ครบถ้วน คือมีบล็อก **`try-catch`**, มีคำสั่ง **`commit`** และมีคำสั่ง **`rollback`** พร้อมทั้งตั้งค่า **Set Isolation Level** ของ Transaction ให้เหมาะสม
